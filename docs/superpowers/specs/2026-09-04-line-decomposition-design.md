# Дизайн: декомпозиция исследования на 3-5 линий с параллельными субагентами

Дата: 2026-09-04
Статус: утверждён в брейншторме

## Проблема

Сейчас один Researcher делает всю работу сам: берёт бриф и в одном цикле tool calling ищет, читает, записывает находки. Вся работа — в одном контексте одной модели. Контекст растёт (результаты всех поисков, все прочитанные страницы), модель «тупеет» и дорожает.

## Цель

Каждую research-задачу агент декомпозирует на 3-5 линий (под-вопросов). Каждую линию исследует отдельный субагент, который приносит главному только саммари + источники. Это классический паттерн «lead researcher + sub-agents» (Anthropic, «How we built our multi-agent research system»).

## Архитектура

```
runResearch (main.go)
  ├─ Clarifier → вопросы → ответы                    [не меняется]
  ├─ buildBrief                                      [не меняется]
  ├─ Lead Researcher (переделанный Researcher.Run)
  │     ├─ (опц.) ask_user_tool — вопрос до планирования
  │     ├─ Planner → 3-5 линий {title, question}
  │     ├─ N субагентов ПАРАЛЛЕЛЬНО (goroutine + WaitGroup)
  │     │     каждый: свой цикл tool calling (search/read/add_finding/finish)
  │     │     находки → общая сессия; возвращает {summary, sources}
  │     └─ Синтез: 1 LLM-вызов из всех саммари → общая картина
  └─ Reporter: отчёт из находок + синтез, verifyLinks остаётся
```

## Компоненты

### Planner (новый файл `internal/agents/planner.go`)

Агент-планировщик. Один LLM-вызов, JSON-ответ (как Clarifier).

- `Plan(ctx, brief) ([]Line, error)`, где `Line{Title, Question string}`
- Промпт: из брифа + ответов пользователя выделить 3-5 независимых линий. Каждая линия — конкретный под-вопрос, который можно исследовать отдельно, не пересекаясь с другими.
- Формат ответа: `{"lines": [{"title": "...", "question": "..."}]}`
- Правила: 3-5 линий; линии не пересекаются (иначе субагенты дублируют поиски); каждая линия — конкретный под-вопрос, а не «разобраться в теме»; простой бриф → 3 линии, сложный → 5.
- Обработка ошибок: невалидный JSON или 0 линий → fallback: одна линия = весь бриф. Прогон не падает.

### Субагент линии (новый файл `internal/agents/line.go`)

Функция, запускающая цикл tool calling для одной линии.

- `runLine(ctx, sess, line, ...) LineResult`, где `LineResult{Summary string, Sources []string, Err error}`
- Свой `params.Messages` — изоляция контекста: субагент не видит, что искали другие линии. Видит только свою линию + результаты своих поисков.
- Инструменты: `search_tool`, `read_tool`, `add_finding_tool`, `finish_tool`. **Без** `ask_user_tool` — параллельные субагенты не должны драться за `AnswerCh`.
- `add_finding_tool` пишет в общую сессию (как сейчас) + в локальный список линии (для `Sources`).
- `finish_tool` → `LineResult{Summary, Sources}`.
- Цикл — тот же, что сейчас в `researcher.go`: проверка лимитов → вызов LLM → выполнение tool calls → повтор.

### Lead Researcher (переделанный `internal/agents/researcher.go`)

- `Run`: планирование → параллельный запуск линий → ожидание (WaitGroup) → синтез.
- `ask_user_tool` остаётся у главного, вызывается **до** планирования (ответ уходит в бриф). Вопросы посреди уже запущенных линий не поддерживаются.
- Синтез: один LLM-вызов из всех саммари → финальный `summary` (что известно, противоречия, пробелы).
- Упавшая линия не роняет прогон: `LineResult{Err}` → синтез учитывает «линия X не исследована».

### Reporter (минимальные изменения `internal/agents/reporter.go`)

- В контекст отчёта добавляется синтез (`## Синтез`).
- Промпт и `verifyLinks` не меняются — Reporter по-прежнему пишет только из находок «факт+URL», гарантия «не выдумать ссылку» сохраняется.

### Session (`internal/research/session.go`)

- Новое поле `Synthesis string` — чтобы передать синтез от Lead Researcher в Reporter.

### Events (`internal/events/events.go`)

- Новый тип события `lines` + `hub.Lines(id, titles []string)`.

### main.go

- Создать Planner, передать в `NewResearcher`.

### Config (`internal/config/config.go`)

- Поднять дефолты: `MAX_SEARCHES` 8→15, `MAX_PAGES_READ` 10→20 (общий пул теперь делят 3-5 линий).

## Ключевые решения

| Вопрос | Решение |
|---|---|
| Параллельность | Параллельно (goroutine + WaitGroup) |
| Передача находок | Субагенты пишут в общую сессию через `add_finding_tool` |
| Лимиты | Общий пул на сессию (счётчики уже под mutex) |
| После линий | Синтез саммари одним LLM-вызовом |
| Когда заканчивать | Субагент сам через `finish_tool` + жёсткие лимиты сверху |
| Вопрос посреди исследования | Только у главного, до планирования линий |

## Тестирование

Чтобы тестировать агентов, нужны интерфейсы вместо конкретных клиентов:
- `internal/llm` — интерфейс `{Chat, ChatJSON}` (агенты зависят от него, тесты — фейки)
- `internal/tools` — интерфейс `{Search}` для Exa

Тесты:
- `planner_test.go` — парсинг JSON, fallback при ошибке/0 линий
- `line_test.go` — цикл, лимиты, finish_tool, изоляция контекста
- `researcher_test.go` — оркестрация: параллельный запуск, синтез, упавшая линия

## Вне скоупа

ThinReport enforcement, rate-limit, утечка сессий, handleAnswer — остаются как известные пробелы, не смешиваются с этой задачей.
